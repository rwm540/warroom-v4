# سرویس OTP و IPPanel در WarRoom V4

این فایل فقط قرارداد و مسیرهای فعال در مخزن را خلاصه می‌کند؛ **آماده‌بودن Production یا تحویل واقعی پیامک را تأیید نمی‌کند**. معماری و محدودیت‌ها در [docs/deployment-auth.md](docs/deployment-auth.md) توضیح داده شده‌اند.

## مسیر فعال

- Entry point سرور: `server_node/src/index.js`
- Routeهای OTP: `server_node/src/routes/otp.js`
- سرویس SMS: `server_node/src/lib/sms.js`
- تنظیمات: `server_node/src/config.js`
- Supabase: `server_node/src/lib/supabase.js`
- فرانت‌اند از مسیرهای same-origin زیر استفاده می‌کند:
  - `POST /api/otp/send`
  - `POST /api/otp/verify`
  - `POST /api/otp/resend`
- Nginx این سه مسیر OTP و `GET /api/health` را با location اختصاصی به Node روی شبکه خصوصی Docker هدایت می‌کند و بقیه مسیرهای `/api/` (از جمله `/api/session` و `/api/admin`) را با همان سرویس خصوصی پروکسی می‌کند؛ `GET /api/health` زمان‌بندی جداگانه دارد. API Node پورت عمومی میزبان ندارد.
- ثبت‌نام و ورود همچنان از Supabase RPC فرانت‌اند انجام می‌شود؛ Node سرویس عمومی مدیریت کاربران نیست.

## قرارداد OTP

OTP دقیقاً شش رقم است. مقدار پیش‌فرض اعتبار `OTP_TTL_SECONDS` برابر **۱۲۰ ثانیه** است. همان مهلت مطلق برای `expires_at` در Supabase، `exp` توکن چالش و تایمر مرورگر استفاده می‌شود: پاسخ سرور هم `expiresIn` (ثانیهٔ باقی‌مانده) و هم `expiresAt` (مهلت مطلق ISO) و `resendAvailableIn` (کول‌داون ارسال مجدد) را برمی‌گرداند و مودال از همان مهلت مطلق می‌شمارد، بنابراین بستن و بازکردن پنجره عمر کد را تمدید نمی‌کند. متن SMS مدت اعتبار را به ثانیه از زمان صدور بیان می‌کند. چالش به شناسه کاربر، شناسه درخواست و HMAC کد ملی مقید است؛ کد OTP به‌صورت HMAC ذخیره می‌شود و پس از تأیید یا پایان تلاش‌ها قابل استفاده مجدد نیست. کدی که از مهلت گذشته باشد هم در لایهٔ امضای توکن و هم در تابع `warroom_verify_otp` (`expires_at > now()`) رد می‌شود.

## قرارداد ارسال مجدد

`POST /api/otp/resend` همان handler محافظت‌شدهٔ `POST /api/otp/send` را اجرا می‌کند؛ بنابراین محدودیت‌ها در ارسال مجدد هم برقرار است:

- `purpose: "login"`: رمز عبور **دوباره اجباری** است و پیش از ارسال هر پیامک روی سرور بررسی می‌شود (رمزپایه‌بودن ورود با OTP حفظ می‌شود). اگر رمز نیامده باشد یا درست نباشد، پاسخ یکسان `401 INVALID_CREDENTIALS` و بدون ارسال پیامک است.
- `purpose: "registration"`: با کد ملی و تنها در صورت وجود ثبت‌نام موقت معتبر کار می‌کند.
- کول‌داون `OTP_RESEND_COOLDOWN_SECONDS` (پیش‌فرض ۶۰ ثانیه) با پاسخ `429 OTP_RESEND_COOLDOWN` و `retryAfterSeconds`/`Retry-After` گزارش می‌شود؛ سقف IP و سقف هر کد ملی در ۱۵ دقیقه هم دست‌نخورده اعمال می‌شوند.
- بستن پنجرهٔ OTP در مرورگر هیچ چالشی را باطل نمی‌کند و هیچ حسابی قفل نمی‌شود؛ کاربر می‌تواند بعداً دوباره کد جدید دریافت کند (تنها محدودکننده، همان کول‌داون و سقف‌های سروری است).

## بررسی تحویل پیامک

`deliveryStatus: "accepted"` در پاسخ سرویس به معنای پذیرش درخواست توسط IPPanel است، نه تحویل به گوشی. روش قطعی بررسی تحویل هر پیام (گزارش `by_bulk` و `recipients`، معناهای `message_status`، ابزار خط فرمان، endpoint مدیریتی و جدول تفکیک خطاها) در [docs/otp-sms-delivery.md](docs/otp-sms-delivery.md) آمده است.

## قرارداد IPPanel

کد از Edge Webservice API رسمی IPPanel استفاده می‌کند: [`POST /v1/api/send`](https://ippanelcom.github.io/Edge-Document/docs/send/webservice/). درخواست شامل `Authorization`، فرستنده و گیرنده E.164، متن پیام و `params.recipients` است. موفقیت فقط با پاسخ HTTP موفق، `meta.status === true` و شناسه معتبر در `data.message_outbox_ids` پذیرفته می‌شود. درخواست خروجی timeout برابر ۱۵ ثانیه دارد و timeout خواندن Nginx برای API برابر ۳۰ ثانیه است؛ پاسخ موفق Provider، تحویل قطعی به تلفن را اثبات نمی‌کند.

خطاها به کدهای مستقل تفکیک شده‌اند تا «پیکربندی ناقص»، «فرستندهٔ تأییدنشده»، «کلید نامعتبر»، «محدودیت نرخ Provider»، «رد گیرنده/متن» و «خطای شبکه» از هم قابل تشخیص باشند. شناسهٔ پیام Provider در `warroom_otp_codes.sms_message_id` ذخیره می‌شود و لاگ‌ها فقط شامل کد خطا، وضعیت HTTP، کد خطای Provider و شمارهٔ ماسک‌شده‌اند؛ کد OTP، کلید API، رمز، کد ملی، شمارهٔ کامل و بدنهٔ پاسخ Provider هرگز Log نمی‌شوند.

کلید فقط در متغیر خصوصی سمت Node به نام `IPPANEL_API_KEY` قرار می‌گیرد. فرستنده و URL از `IPPANEL_FROM_NUMBER` و `IPPANEL_API_URL` سمت سرور خوانده می‌شوند. هیچ مقدار واقعی یا کلیدی در این مخزن قرار ندهید.

## Supabase و محدودیت‌های فعلی

جداول `warroom_otp_codes` و `warroom_otp_rate_limits` و امضای RPCهای استفاده‌شده در Migrationهای موجود تعریف شده‌اند. دسترسی OTP در Migrationها برای `service_role` محدود شده است. بااین‌حال، Migration پایه برای `warroom_users` هنوز دسترسی مستقیم گسترده و Policyهای `USING (true)` دارد؛ این موضوع می‌تواند کد ملی و شماره همراه را در معرض کلاینت بگذارد و مانع جداگانه Production است. رفع آن نیازمند بازبینی جریان‌های مستقیم Supabase فرانت‌اند است و در این تغییر انجام نشده است. همچنین فرانت‌اند و Node رقم کنترلی کد ملی را بررسی می‌کنند، اما RPC ثبت‌نام `warroom_register_user` در Migration فقط طول/رقمی‌بودن را می‌سنجد و از `anon` قابل فراخوانی است؛ فراخوانی مستقیم می‌تواند رکوردی بسازد که OTP آن را رد می‌کند. قرارداد RPC باید در Migration بازبینی‌شده هم‌راستا شود. همچنین endpointهای Node برای `purpose: "login"` (هم در `/api/otp/send` و هم در `/api/otp/resend`) رمز را اجباری می‌گیرند و پیش از هر ارسال با RPC `warroom_verify_login` روی سرور بررسی می‌کنند، بنابراین ارسال مجدد راهی برای دورزدن رمز نیست؛ Migration برای RPCهای مدیریتی `anon` را با OTP مدیر مجاز می‌کند. بنابراین این پیاده‌سازی به‌تنهایی الزام دو عاملی رمز+پیامک را تضمین نمی‌کند و پیش از Production باید این مرز احراز هویت بازطراحی شود. تطبیق فقط ایستا است؛ هیچ SQL/Migration یا اتصال به پایگاه داده واقعی انجام نشده است.

**مانع Build/CI باقی‌مانده:** `server_node/package-lock.json` در مخزن وجود ندارد، در حالی که CI و Docker برای API از `npm ci` استفاده می‌کنند. فایل `.gitignore` دیگر Lock را نادیده نمی‌گیرد، اما Lock معتبر از روی Manifest تولید نشده است. تا تولید و ثبت Lock واقعی از مسیر مجاز، نصب API و Build تصویر آن قابل تأیید نیست؛ Lock ساختگی ارائه نمی‌شود.

تست، Build، Docker، SQL/Migration، اتصال زنده به دیتابیس، ارسال پیامک واقعی یا Deployment اجرا نشد و نصب اختصاصی API نیز انجام نگرفت. به‌اشتباه، هنگام ساخت PR یک `npm ci` در ریشه مخزن اجرا شد و npm گزارش کرد ۵۰۵ بسته نصب شده‌اند؛ این کار برخلاف محدودیت درخواست‌شده بود و تکرار نمی‌شود. نصب ناخواسته lockfile را نساخت یا تغییر نداد.
