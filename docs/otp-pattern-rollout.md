# OTP pattern rollout (review required before production)

## Contracts and prerequisites

The server uses the existing `warroom_users`, `warroom_pending_registrations`, `warroom_otp_codes`, `warroom_refresh_tokens` and service-role-only auth RPCs. The registered sender and pattern are **not** secrets: `+983000505`, `mf31w8ng9vnoqy5`. Set `IPPANEL_API_KEY` (existing variable name), `IPPANEL_FROM_NUMBER`, `IPPANEL_PATTERN_CODE`, `OTP_TTL_SECONDS=120`, `OTP_RESEND_COOLDOWN_SECONDS=120` in the **server's** secret environment. Do not place the token in the web build. Missing pattern configuration fails closed; there is no webservice or simulated-delivery fallback. Ensure the sender and pattern are assigned to the provider account. Never include OTP, credentials, token, full phone or national code in logs.

The official [Edge pattern API](https://ippanelcom.github.io/Edge-Document/docs/send/pattern/) specifies `POST /v1/api/send`, `Authorization` token, `sending_type: pattern`, top-level `code` as the pattern identifier, a single top-level `recipients` array and `params.code` as the OTP string. HTTP success plus `meta.status === true` and nonempty valid `data.message_outbox_ids` means **accepted**, not delivered. Network/timeout ambiguity is not retried automatically. [IPPanel API reference](https://apidoc.ippanel.com/) also lists send and report APIs; `docs.ippanel.com/docs/` returned 502 during review. Provider reporting is not part of this change and no unverified status endpoint is called. Investigate undelivered messages through provider reports keyed by the stored `sms_message_id` without exposing IDs or phone numbers to browsers.

## Flow

1. IP and national-code rate limits (12/IP/15min, 3/national-code/15min, 120s cooldown by national code; 10 login credential attempts/15min) are checked server-side. The login RPC verifies password and account status; registration requires an unexpired pending record. Both retrieve the phone from the server database. The browser's role/phone do not select the recipient.
2. Node generates one six-digit cryptographically random string (including leading zeros), derives its keyed hash, and calls `warroom_issue_otp_challenge`. The new RPC locks per national code and atomically invalidates old **unverified** challenges and inserts the new row. No SMS is attempted if this fails. It requires the migration below.
3. The same code is passed to the pattern provider. On acceptance the outbox ID is saved to the row. The verification RPC only considers unexpired, unused challenges with an outbox ID. Provider rejection, invalid response, unknown network outcome, or inability to store the ID fails the request and attempts invalidation; no blind retry is performed. Acceptance is not proof of handset delivery.
4. `warroom_verify_otp` compares keyed hashes under a row lock, counts failed attempts (maximum 5) and consumes correct codes atomically. `/api/session/create` checks the short-lived proof, finalizes registration when applicable, atomically consumes the proof, loads the current account and creates a database-backed session with HttpOnly cookie. It does not trust the browser role. Session creation/database failures must not return success.
5. UI derives its one countdown from the server's absolute `expiresAt`; resend requires password again for login and starts a new deadline only after a successful server response. Closing the modal does not modify the deadline; a page refresh loses the in-memory challenge and requires a fresh request subject to server cooldown. No OTP or proof is persisted in browser storage.

## Required migration and deployment

**Do not run against production as part of review.** `supabase/migrations/20261015000000_atomic_otp_issue_and_delivery_gate.sql` is necessary because the old invalidate/insert operations were separate HTTP transactions, allowing simultaneous sends to leave multiple active codes; the old verify RPC also allowed verifying an SMS before provider acceptance. It modifies only two service-role RPCs; no new table or browser grants. Review SQL and run in a staging Supabase project with preceding migrations applied; verify service-role execution, row locking under concurrent issuances, SMS-ID gating, RLS, session creation and `GET /api/ready` before scheduling a separate production migration and server rollout. **Deploy migration before API**; old API remains compatible with the gated verifier because it saves message IDs. Rollback: stop new sends, restore previous API release and prior RPC definitions via a reviewed migration (do not simply drop the issue RPC while new API is running); invalidate outstanding challenges before reopening sends. The added Footer is a static web change and can be reverted by rolling back the web release.

**Not validated here:** live Supabase migration, provider acceptance/delivery, SMS sender assignment, and staging sessions: no safe staging credentials/services were available. Mocked integration tests do not prove live behavior.

## Open product conflict: 25 characters

Approved pattern text is `کد ورود هیئت نوالهدا: %code%`. Replacing the placeholder with any six ASCII digits produces **28 Unicode code points** (test sample `123456` is only a length fixture, not a production OTP). JavaScript UTF-16 length is also 28 for this particular text; Unicode grapheme, UTF-16 and provider GSM/UCS-2 segment limits are different concepts. Provider message segmentation/billing must be confirmed separately in the panel. If the prior **25-character** product limit remains mandatory, this is an **unresolved requirement conflict**. Do not shorten the approved pattern or create a new one without product/provider approval. No 120-second or promotional text is appended to the approved SMS.
