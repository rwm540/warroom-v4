> **به‌روزرسانی پترن فعال:** ارسال OTP اکنون فقط با Pattern API و `IPPANEL_PATTERN_CODE` انجام می‌شود؛ تمام اشاره‌های تاریخی این سند به متن آزاد/`webservice` یا mock ارسال، برای ارسال OTP معتبر نیستند. جزئیات و تعارض ۲۵ نویسه: [otp-pattern-rollout.md](otp-pattern-rollout.md). بخش‌های گزارش تحویل همچنان برای شناسهٔ outbox کاربرد دارند.

# بررسی تحویل پیامک OTP (IPPanel) و استقرار دستی

این سند فقط دربارهٔ **ارسال و تحویل پیامک کد تأیید** است و پاسخ قطعی می‌دهد به این پرسش‌ها:

1. پاسخ موفق `POST /api/otp/send` دقیقاً چه چیزی را اثبات می‌کند؟
2. اگر پیامک به گوشی نرسید، چگونه علت را از هم جدا کنیم؟
3. وضعیت تحویل یک پیام مشخص را چگونه و با چه دستوری بررسی کنیم؟
4. استقرار دستی و بازگشت به نسخهٔ قبلی چگونه انجام می‌شود؟

> هیچ مقدار محرمانه‌ای (`IPPANEL_API_KEY`، رمزها، توکن‌ها، کد OTP، شمارهٔ کامل تلفن) نباید در لاگ، تیکت پشتیبانی یا خروجی دستورها چاپ شود. ابزارهای زیر عمداً فقط داده‌های پاک‌سازی‌شده و ماسک‌شده برمی‌گردانند.

## ۱) «پذیرش درخواست» با «تحویل پیامک» یکی نیست

`POST /v1/api/send` تنها زمانی در این سرویس موفق محسوب می‌شود که **همهٔ** شرط‌های زیر برقرار باشند:

- پاسخ HTTP موفق باشد،
- `meta.status === true` باشد،
- `data.message_outbox_ids` حداقل یک شناسهٔ عددی معتبر داشته باشد.

این یعنی IPPanel درخواست را **پذیرفته و در صف گذاشته است** (accepted). پاسخ API هیچ‌گاه اثبات نمی‌کند که:

- پیام از سوی اپراتور پذیرفته شده،
- به گوشی کاربر تحویل شده،
- خط فرستنده در حساب IPPanel تأیید شده است.

به همین دلیل پاسخ موفق `/api/otp/send` شامل `deliveryStatus: "accepted"` است و متن پیام کاربر هم می‌گوید «تحویل نهایی به اپراتور وابسته است». شناسهٔ پیام (`message_outbox_ids[0]`) در ستون `sms_message_id` چالش در `warroom_otp_codes` ذخیره می‌شود تا بعداً بتوان همان پیام را در گزارش‌های IPPanel ردیابی کرد.

## ۲) ثبت امن نتیجهٔ ارسال

| رویداد | کجا ثبت می‌شود | چه چیزی ثبت نمی‌شود |
| --- | --- | --- |
| پذیرش پیام | لاگ سرور: `[sms] accepted messageId=… validitySeconds=… phone=0912***33` و ستون `sms_message_id` | کد OTP، کلید API، بدنهٔ پاسخ Provider، شمارهٔ کامل |
| رد شدن پیام | لاگ سرور: `[sms] rejected code=SMS_SENDER_REJECTED httpStatus=422 providerCode=400-2 phone=0912***33` | متن خطای Provider، بدنهٔ درخواست/پاسخ، کلید |
| خطای شبکه/تایم‌اوت | لاگ سرور: `[sms] transport failure code=SMS_NETWORK_FAILED reason=… phone=0912***33` | بدنهٔ درخواست (شامل کد OTP) |
| خطای ۵xx مسیرها | `[warroom-otp-api] CODE status=… path=…` | بدنهٔ درخواست، کد ملی، رمز، توکن |

## ۳) تفکیک خطاها

هر خطای ارسال یک کد مستقل دارد (پیام فارسی امن آن در `server_node/src/app.js` تعریف شده است):

| کد | معنا | کار درست |
| --- | --- | --- |
| `SMS_NOT_CONFIGURED` | `IPPANEL_API_KEY` یا `IPPANEL_FROM_NUMBER` تنظیم نشده | متغیرهای محیطی سرور را کامل کنید |
| `SMS_CONFIGURATION_INVALID` | `IPPANEL_API_URL` غیرمجاز است (فقط `https://edge.ippanel.com/v1/api/send` پذیرفته می‌شود) | مقدار URL را اصلاح کنید |
| `SMS_SENDER_INVALID` | قالب `IPPANEL_FROM_NUMBER` معتبر نیست (باید E.164 باشد) | شمارهٔ فرستنده را با قالب `+983000505` بنویسید |
| `SMS_AUTH_REJECTED` | توکن/کلید IPPanel پذیرفته نشد | کلید API را در حساب IPPanel بازبینی کنید |
| `SMS_SENDER_REJECTED` | IPPanel خط فرستنده را برای این حساب نپذیرفت | شمارهٔ فرستنده را در حساب IPPanel تخصیص/تأیید کنید |
| `SMS_RECIPIENT_REJECTED` | شمارهٔ مقصد از سوی Provider معتبر نیست | شمارهٔ ثبت‌شدهٔ کاربر در `warroom_users` را اصلاح کنید |
| `SMS_MESSAGE_REJECTED` | متن پیام پذیرفته نشد (مثلاً بلوک‌شدن الگو) | متن/الگو را با سیاست IPPanel تطبیق دهید |
| `SMS_PROVIDER_RATE_LIMITED` | خود IPPanel درخواست را محدود کرده | ظرفیت حساب یا فاصلهٔ ارسال را بررسی کنید |
| `SMS_PROVIDER_UNAVAILABLE` | اختلال ۵xx در Provider | چند دقیقه بعد دوباره تلاش کنید |
| `SMS_NETWORK_FAILED` | تایم‌اوت/خطای شبکه یا DNS | دسترسی خروجی سرور به `edge.ippanel.com` را بررسی کنید |
| `SMS_SEND_FAILED` | پاسخ نامعتبر/غیرقابل‌تفسیر، یا `meta.status !== true` | گزارش Provider را با شناسهٔ پیام بررسی کنید |
| `OTP_RESEND_COOLDOWN` (HTTP 429) | درخواست کد جدید پیش از پایان کول‌داون | پیام شامل ثانیه‌های انتظار و هدر `Retry-After` است |
| `RATE_LIMITED` (HTTP 429) | سقف IP یا سقف کد ملی در ۱۵ دقیقه | منتظر بمانید؛ این محدودیت‌ها حذف نمی‌شوند |
| `SMS_STATUS_UNAVAILABLE` | بررسی تحویل ممکن نیست (Provider پیکربندی نشده یا شناسه ثبت نشده) | تنظیمات و شناسهٔ پیام را بررسی کنید |

در همهٔ این حالت‌ها چالشی که پیامک آن پذیرفته نشده **باطل** می‌شود تا کد بدون‌تحویل ولی قابل‌استفاده باقی نماند.

## ۴) بررسی قطعی تحویل یک پیام

IPPanel برای همین کار دو گزارش مستند دارد:

- گزارش کلی: `GET /v1/api/report/by_bulk?messages_outbox_id=<id>`
- گزارش گیرندگان: `GET /v1/api/report/recipients?bulk_id=<id>&page=1&per_page=30`

مقدار `message_status` در گزارش گیرندگان:

| مقدار | معنا |
| --- | --- |
| `0` | به اپراتور ارسال شد (Sent to the operator) |
| `1` | اپراتور پیام را دریافت کرد (Operator received) |
| `2` | **به گیرنده تحویل شد** (Delivered) |
| `3` | تحویل نشد (Not delivered) |
| `4` | شماره در لیست سیاه است (Blacklisted) |

### الف) خط فرمان (ساده‌ترین راه)

```bash
# همان محیط خصوصی سرور (server_node/.env یا متغیرهای تزریق‌شده) لازم است
node server_node/scripts/check-sms-status.mjs 1123544244
node server_node/scripts/check-sms-status.mjs --challenge <challenge_uuid>
```

خروجی فقط شامل وضعیت کلی، شمارنده‌ها و گیرندگان **ماسک‌شده** است؛ کلید و شمارهٔ کامل چاپ نمی‌شود.
اگر `deliveredToHandset` برابر `true` باشد، همهٔ گیرندگانِ بازیابی‌شده وضعیت `2` دارند.

### ب) از داخل سامانه (فقط مدیر)

```bash
POST /api/admin/otp/sms-status
{ "messageId": "1123544244" }      # یا { "challengeId": "<uuid>" }
```

این مسیر نیازمند نشست مدیر + هدر CSRF است و خروجی ماسک‌شده برمی‌گرداند. برای کاربر عادی `403` و برای درخواست بدون نشست `401` است.

### ج) بررسی مستقیم با curl (فقط روی سرور خصوصی)

```bash
curl -s --location \
  'https://edge.ippanel.com/v1/api/report/recipients?bulk_id=<id>&page=1&per_page=30' \
  --header 'Authorization: <IPPANEL_API_KEY>'
```

این دستور را هرگز روی ماشین محلی/اشتراکی یا در تیکت پشتیبانی اجرا نکنید؛ کلید API در تاریخچهٔ shell ذخیره می‌شود.

## ۵) اگر پیامک نرسید، این ترتیب را بررسی کنید

1. **قابل‌مشاهده‌بودن خطا:** پاسخ `/api/otp/send` را از تب Network مرورگر ببینید. `429` یعنی محدودیت، `502/503` یعنی خطای Provider/پیکربندی.
2. **کد خطا در لاگ سرور:** با کد جدول بخش ۳ علت را مشخص کنید.
3. **تأیید پذیرش:** وجود `messageId` در لاگ `[sms] accepted` و مقدار `sms_message_id` یعنی Provider پیام را پذیرفته است.
4. **گزارش تحویل:** با بخش ۴ وضعیت همان پیام را بخوانید:
   - `message_status = 2` → پیام به گوشی تحویل شده؛ مشکل در سمت کاربر است (سیم‌کارت دوم، فیلتر پیامک‌های تبلیغاتی، حالت پرواز، اسپم گوشی).
   - `message_status = 3` → تحویل نشد: خاموش‌بودن گوشی، عدم دسترسی شبکه، یا فیلتر اپراتور.
   - `message_status = 4` → شماره در لیست سیاه Provider است (کاربر پیامک‌های تبلیغاتی را لغو کرده یا اپراتور مسدود کرده).
   - `message_status = 0/1` → هنوز در حال تحویل است؛ چند دقیقه بعد دوباره بررسی کنید.
   - نبودِ ردیف گیرنده در گزارش → پیام هرگز به دست اپراتور نرسیده است.
5. **شمارهٔ فرستنده:** اگر `state` در گزارش `by_bulk` پایان یافته است ولی همهٔ گیرندگان `3` هستند، اولویت اول بررسی «شمارهٔ فرستندهٔ تأییدشده» و «کیفیت مسیر» در پنل IPPanel است.
6. **ارسال انبوه ناخواسته:** محدودیت‌های `OTP_MAX_SEND_PER_15MIN`، `OTP_RESEND_COOLDOWN_SECONDS` و سقف IP عمداً فعال‌اند؛ رخداد `429` طبیعی است و نباید با «نرسیدن پیامک» اشتباه گرفته شود.

## ۶) استقرار دستی (Production)

پیش‌نیاز: دسترسی به سرور، فایل `.env` واقعی روی سرور (هرگز داخل Git)، و پشتیبان‌گیری از نسخهٔ فعلی.

1. **پشتیبان‌گیری و مهر زمانی نسخهٔ فعلی**
   ```bash
   cd /path/to/warroom-v4
   git rev-parse HEAD | tee /tmp/warroom-previous-revision.txt
   git status --porcelain   # باید خالی باشد
   ```
2. **آوردن تغییرات** (بدون تغییر مستقیم روی Production):
   ```bash
   git fetch origin
   git checkout <branch-or-tag-این-تغییر>
   git log --oneline -1
   ```
3. **تنظیم متغیر محیطی روی سرور** (فقط در `.env` سرور، نه در مخزن):
   ```
   OTP_TTL_SECONDS=120
   ```
   اگر این متغیر ست نشده باشد هم پیش‌فرض کد از این پس ۱۲۰ ثانیه است؛ ست‌کردن صریح باعث شفافیت می‌شود.
   سایر مقادیر OTP/پیامک را دست‌نخورده بگذارید.
4. **ساخت و بالا آوردن سرویس‌ها**
   ```bash
   npm ci                     # ریشه (فرانت‌اند)
   npm ci --prefix server_node
   npm run build
   docker compose --env-file .env up -d --build
   docker compose ps
   ```
5. **بررسی سلامت پیش از اعلام موفقیت**
   ```bash
   curl -s https://<domain>/api/health
   curl -s https://<domain>/api/ready | head -c 400   # باید ready:true بدهد
   ```
   هیچ SQL/Migration جدیدی برای این تغییر لازم نیست؛ فقط اگر Migrationهای قبلی اعمال نشده‌اند، `ready` هشدار می‌دهد.
6. **آزمون دود (Smoke) با یک شمارهٔ تستی واقعی**
   - درخواست کد برای یک حساب تستی،
   - بررسی تایمر ۱۲۰ ثانیه‌ای در UI،
   - «ارسال مجدد» پس از ۶۰ ثانیه برای هر دو مسیر ورود و ثبت‌نام،
   - بررسی تحویل با بخش ۴،
   - بستن و بازکردن پنجره و درخواست کد جدید.

## ۷) بازگشت به نسخهٔ قبلی (Rollback)

1. بازگشت کد به نسخهٔ قبلی:
   ```bash
   cd /path/to/warroom-v4
   git checkout "$(cat /tmp/warroom-previous-revision.txt)"   # یا tag نسخهٔ قبلی
   npm ci && npm ci --prefix server_node && npm run build
   docker compose --env-file .env up -d --build
   ```
2. بازگشت مقدار محیطی (اختیاری): اگر می‌خواهید اعتبار کد به مقدار قبلی برگردد، در `.env` سرور `OTP_TTL_SECONDS=300` بگذارید و سرویس API را دوباره بالا بیاورید.
3. داده‌ها و Migration: این تغییر هیچ جدول/ستون/Policy جدیدی اضافه نکرده است؛ بنابراین rollback پایگاه داده لازم نیست و ردیف‌های `warroom_otp_codes` قدیمی خودشان با `expires_at` منقضی می‌شوند.
4. بررسی پس از rollback: `GET /api/health` و یک ارسال آزمایشی؛ سپس همان روش بخش ۴ برای تأیید تحویل.
